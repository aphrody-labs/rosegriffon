# Audit `@rg/ui` — 2026-05-17

> Audit lecture-seule des 55 composants shadcn (style new-york) migrés depuis
> `vps/apps/rosegriffon/src/components/ui/` vers `~/rg/packages/ui/src/components/`.
> Aucun code n'a été modifié.

## Synthèse

Le package est **fonctionnel et compile** (type-check vert, deps complètes), mais **mélange deux générations shadcn dans un même barrel** : ~80 % des composants utilisent le pattern moderne (function components, `data-slot`, `React.ComponentProps<typeof X>`) et ~20 % le pattern legacy (`React.forwardRef` + `React.ElementRef` + pas de `data-slot`). Cette dette de cohérence empêche un theming uniforme par sélecteur `[data-slot=…]` et bloque les futurs styles globaux. **3 composants posent des problèmes critiques** : `scroll-area` (ne wrappe PAS Radix — c'est un simple `<div overflow-auto>`), `sonner` (`theme="light"` hardcodé, ignore le contexte), `responsive-dialog` (custom non-upstream sans footer slot). Les tokens `--rg-marine`/`--rg-rose`/`--rg-griffon` ne sont **jamais consommés par les composants** — ils existent dans `styles.css` mais aucun composant ne les utilise comme valeurs par défaut. La DA Rose Griffon est donc inerte tant que les apps ne re-mappent pas explicitement `--primary` → `--rg-rose` dans leur `globals.css`.

## Composants à améliorer (18 / 55)

### Critiques

#### `scroll-area.tsx` — divergence majeure
Le composant n'utilise **pas** `@radix-ui/react-scroll-area` (et le package n'est même pas dans `package.json`). Il rend un simple `<div className="relative overflow-auto">` avec un `ScrollBar` qui est aussi un `<div>` purement décoratif (non interactif, non lié au scroll réel du parent). Conséquences :
- Pas de scrollbar personnalisée cross-browser (le navigateur impose le sien).
- `ScrollBar` n'a aucun comportement — c'est mort visuellement.
- Toute app qui s'attend au comportement Radix (touch-action, focus trap, momentum iOS) cassera.

**Recommandation** : ajouter `@radix-ui/react-scroll-area: ^1.2.x` aux deps + réinstaller via `bunx --bun shadcn@latest add scroll-area` (et écraser ce fichier).

#### `sonner.tsx` — `theme="light"` hardcodé
```tsx
<Sonner theme="light" ... />
```
- Le toast restera blanc même quand `apps/azalee` passera son root en `.dark`.
- Le code upstream est `theme={theme as ToasterProps["theme"]}` où `theme` vient de `useTheme()` (`next-themes`).
- Comme **ni `apps/website` ni `apps/azalee` n'utilisent `next-themes`** (website : `Providers` sans theme, azalee : `ThemeProvider` custom localStorage), un fix simple = lire la classe `<html>` (`document.documentElement.classList.contains('dark')`) ou prendre une prop `theme`. Sinon importer `next-themes` (cohérent shadcn upstream) et l'intégrer dans les deux apps.

**Recommandation** : accepter une prop `theme` (`"light" | "dark" | "system"`) + valeur par défaut depuis `next-themes` si présent, sinon `"light"`. Documenter dans le composant.

#### `responsive-dialog.tsx` — custom non-upstream
Composant inventé localement (n'existe pas dans shadcn) qui multiplexe `Dialog` (desktop) et `Drawer` (mobile) via `useMediaQuery("(min-width: 768px)")`. Problèmes :
- Le `DrawerFooter` est rendu **vide** (commentaire `// Footer buttons are often inside the form`) — c'est du DOM mort.
- L'API ne propose pas de slot footer alors que la version Dialog n'en propose pas non plus → fonctionnellement, on ne peut pas mettre un bouton "Confirmer" en bas sans le shadcn comme enfant du `children`.
- `Dialog` desktop a `max-w-2xl sm:max-w-[600px]` figé — pas configurable via prop.

**Recommandation** : exposer une prop `footer?: ReactNode` + `contentClassName?: string`. Sinon documenter comme deprecated et préférer `Dialog`/`Drawer` directement.

### Pattern legacy (à moderniser pour cohérence)

11 composants utilisent encore le pattern `React.forwardRef<React.ElementRef<typeof X>, React.ComponentPropsWithoutRef<typeof X>>` sans `data-slot` :

| Composant | Manque | Pattern attendu (upstream new-york actuel) |
|---|---|---|
| `alert-dialog.tsx` | `data-slot`, function component | function + `React.ComponentProps<typeof AlertDialogPrimitive.Root>` + `data-slot="alert-dialog-…"` |
| `alert.tsx` | `data-slot`, variant `success`/`warning` | function + `data-slot="alert"`. Upstream a `default` + `destructive` uniquement (variants `success`/`warning` à ajouter localement si besoin) |
| `badge.tsx` | `data-slot`, variant `success`, support `asChild` | upstream récent a `asChild?: boolean` + variants `default/secondary/destructive/outline` (idem ici, OK), mais pas de `data-slot` |
| `checkbox.tsx` | `data-slot`, `CheckIcon` size auto | function + `data-slot="checkbox"` + indicator avec `Check` qui s'auto-size |
| `dialog.tsx` | `data-slot` partout (juste sur close button) | tous les sous-composants devraient avoir `data-slot="dialog-…"` |
| `form.tsx` | `useId` ok mais `useFormState` au lieu de `useFormContext().formState` (actuel) | OK fonctionnellement, juste vérifier compat react-hook-form 7.65 |
| `radio-group.tsx` | `data-slot` | function + `data-slot="radio-group"` / `data-slot="radio-group-item"` |
| `slider.tsx` | `data-slot`, track gradient | upstream récent rend 2 thumbs en mode `value=[min,max]` |
| `table.tsx` | `data-slot`, `sticky` variant header | function + `data-slot="table-…"` ; upstream a `<TableHeader className="sticky top-0 …">` documenté |
| `tabs.tsx` | `data-slot` | function + `data-slot="tabs-list"` / `"tabs-trigger"` / `"tabs-content"` |
| `textarea.tsx` | `data-slot`, classes alignées avec `Input` (utilise encore `ring-offset-background` + `focus-visible:ring-2`) | upstream actuel utilise `focus-visible:ring-ring/50` + `ring-[3px]` comme `Input` |

**Impact réel** : pas de bug runtime, mais l'absence de `data-slot` empêche d'écrire un CSS global type `[data-slot=dialog-content] { @apply rounded-2xl; }` pour appliquer la DA Rose Griffon sans toucher chaque composant.

### Divergences mineures

- **`pagination-controls.tsx`** — composant custom (non shadcn), labels FR hardcodés (`"Précédent"`, `"Suivant"`, `"Page X sur Y"`). Pas i18n-ready. Utilise `<Link>` Next directement → empêche réutilisation hors Next. **Recommandation** : passer `previousLabel`/`nextLabel`/`labelFormat` en props, accepter `LinkComponent` injecté.
- **`pagination.tsx`** — strings FR hardcodés `aria-label="Aller à la page précédente"` + `"Précédent"` + `"Plus de pages"`. Idem.
- **`sheet.tsx`** — `XIcon` au lieu de `X` (upstream actuel), close button utilise encore `ring-offset-background` + `focus:ring-2 focus:ring-offset-2` (pattern legacy).
- **`dialog.tsx`** — close button utilise `ring-offset-background focus:ring-2 focus:ring-ring focus:ring-offset-2` (pattern legacy v3, devrait être `focus-visible:ring-ring/50 ring-[3px]` comme `Input`).
- **`button.tsx`** — variante `link` n'a pas de `hover:text-primary/80`, juste `hover:underline`. Pas grave mais incohérent avec upstream récent.
- **`checkbox.tsx`** + **`radio-group.tsx`** + **`slider.tsx`** + **`tabs.tsx`** : pattern focus legacy `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2`. Upstream new-york actuel utilise `focus-visible:border-ring focus-visible:ring-ring/50 focus-visible:ring-[3px]`. Visuellement plus moderne (anneau soft + bordure colorée), s'accorde mieux avec `:focus-visible` global dans `styles.css` (qui utilise déjà `--rg-rose` en outline).

### Accessibility

- `spinner.tsx` : ✅ `role="status"` + `aria-label="Loading"`. OK.
- `dialog.tsx` / `alert-dialog.tsx` : ✅ Radix gère focus trap. **Mais** `DialogTitle` est `<h2>` implicite via Radix — vérifier qu'aucune app n'override la sémantique heading.
- `pagination.tsx` : `aria-label="pagination"` sur `<nav>` ✅, mais `aria-current="page"` sur `PaginationLink` actif ✅.
- `tabs.tsx` : pas de `aria-orientation` exposé. Radix l'a en interne mais OK.
- `checkbox.tsx` : pas de `aria-label` exposé en API (l'app doit le passer via `…props`). Documenter.
- `alert.tsx` : `role="alert"` OK, mais pas `aria-live="assertive"` (utile pour les destructives qui apparaissent dynamiquement).

## Tailwind v4 issues

### Patterns dépréciés détectés

Aucun `bg-opacity-*` / `text-opacity-*` / `border-opacity-*` (✅).

Mais 8 fichiers utilisent encore le pattern Tailwind v3 `focus:outline-none focus:ring-2 focus:ring-ring focus:ring-offset-2` + `ring-offset-background` :
- `checkbox.tsx:16`
- `slider.tsx:18`
- `tabs.tsx:32`, `tabs.tsx:47`
- `radio-group.tsx:25`
- `sheet.tsx:69` (close button uniquement)
- `dialog.tsx:50` (close button uniquement)
- `textarea.tsx:12`

Tailwind v4 n'a **pas supprimé** ces utilities (elles fonctionnent), mais le pattern moderne shadcn (`focus-visible:border-ring focus-visible:ring-ring/50 focus-visible:ring-[3px]`) est plus accessible (`focus-visible` au lieu de `focus`, ring colorée semi-transparente, bordure indiquant le focus). À aligner pour cohérence visuelle avec les composants déjà à jour (`Button`, `Input`, `Switch`).

### Compatibilité v4 effective

- `@theme inline` est défini dans `apps/website/src/app/globals.css` (✅ pattern v4).
- `@custom-variant dark` est défini (✅).
- `oklch()` utilisé dans `styles.css` (✅ v4 natif).
- Pas d'usage de `tailwindcss-animate` (le composant `accordion` utilise `data-[state=closed]:animate-accordion-up` qui n'est défini nulle part dans `packages/ui/src/styles.css`). **Bug latent** : les keyframes `accordion-up`/`accordion-down` ne sont définies que dans `apps/website/src/app/globals.css` (à vérifier — sinon les accordéons ne s'animent pas dans azalee). À déplacer dans `packages/ui/src/styles.css` ou ajouter `tw-animate-css` aux deps explicites.
- `chart.tsx` cible sélecteurs Recharts par attribut `[stroke='#ccc']` / `[stroke='#fff']` — ces sélecteurs CSS dans `className` sont valides en Tailwind v4 mais fragiles si Recharts change ses defaults. Acceptable.

### Classes potentiellement obsolètes

- `outline-hidden` (vu dans `select.tsx`, `sheet.tsx`, `popover.tsx`, etc.) — c'est `outline-style: hidden` en Tailwind v4 (équivalent v3 `outline-none` mais préservé pour focus visible). ✅ correct.
- `rounded-xs` (`sheet.tsx`) — token Tailwind v4 (`--radius-sm` par défaut). ✅.
- `shadow-xs` — token Tailwind v4. ✅.
- `[--cell-size:--spacing(8)]` (`calendar.tsx`) — utilise la fonction `--spacing()` Tailwind v4. ✅.

**Verdict** : pas de blocker Tailwind v4. Juste un pattern focus legacy à uniformiser.

## Theming recommendations

### État actuel

`packages/ui/src/styles.css` définit 3 tokens branding :
```css
--rg-marine: oklch(0.20 0.05 264);   /* #0c1730 */
--rg-rose:   oklch(0.65 0.22 0);     /* #e91e63 */
--rg-griffon: oklch(0.78 0.13 90);   /* #d4af37 */
```

**Aucun composant ne les consomme.** Le seul usage est dans `:focus-visible { outline: 2px solid var(--rg-rose); }` du même fichier. Les composants utilisent `bg-primary` / `text-primary-foreground` etc., qui résolvent vers les tokens définis dans **chaque app** (cf. `apps/website/src/app/globals.css` qui définit `--primary: oklch(0.205 0 0)` — quasi-noir, pas rose).

Résultat : ces tokens RG sont **morts** — ils existent mais n'influencent ni les composants ni l'aspect visuel.

### Recommandations

**Option A — Re-mapper `--primary` dans `styles.css` (impact toutes apps)**
Ajouter dans `packages/ui/src/styles.css` un bloc `@layer base { :root { --primary: var(--rg-rose); --primary-foreground: oklch(0.98 0 0); … } }` qui sera **écrasé** par les `:root` des apps qui veulent override. Avantage : DA RG par défaut. Inconvénient : casse le visuel actuel (azalee a sa palette aubergine `--azalee-burgundy`).

**Option B (recommandée) — Garder le mapping app-par-app, exposer des composants brandés**
Créer dans `packages/ui/src/components/` quelques wrappers explicites :
- `<RgButton variant="rose|griffon|marine">` qui rend `<Button className="bg-[var(--rg-rose)] text-white hover:bg-[var(--rg-rose)]/90">`.
- `<RgHeader>` qui rend `<header className="bg-[var(--rg-marine)] text-white">`.
- `<RgAccent>` (badge / chip) qui utilise `--rg-griffon`.

Avantage : opt-in, n'affecte pas les `Button` standards qui restent thématiques par app.

**Option C — Wrappers via `data-rg-theme` sur racine**
Définir dans `styles.css` :
```css
[data-rg-theme="rose-griffon"] {
  --primary: var(--rg-rose);
  --primary-foreground: oklch(0.98 0 0);
  --accent: var(--rg-griffon);
  --background: var(--rg-marine);
  --foreground: oklch(0.98 0 0);
}
```
Une app peut alors faire `<div data-rg-theme="rose-griffon">` pour appliquer la palette RG complète à un sous-arbre. Compatible avec le pattern `.dark`/`.azalee`/`.roy` existant côté website.

### Pack Personnage Patreon (cf. `apps/website/patreon.md`)

Si le mapping `niveau-roy → bleu pâle`, `niveau-evans → vert d'eau`, etc. est validé, créer un thème `.patreon-pack` dans `styles.css` avec :
```css
.patreon-pack {
  --background: oklch(0.18 0.06 264);  /* #0c1730 marine nuit */
  --foreground: oklch(0.98 0 0);
  --primary: oklch(0.78 0.13 90);      /* #c9a958 doré */
  --primary-foreground: oklch(0.18 0.06 264);
  --accent: oklch(0.65 0.22 25);       /* #e54a4a rouge corail */
  --secondary: oklch(0.75 0.06 220);   /* #aac9d9 rose/turquoise pâle */
  /* … chart-1..5, sidebar-* */
}
```
Le tier `niveau-evans` peut surcharger localement via `<div className="patreon-pack" style={{"--accent": "oklch(0.65 0.10 165)"}}>` (vert d'eau).

## Dark mode / theme switching

- **`next-themes` n'est pas installé** dans `packages/ui` ni dans les apps.
- `apps/website` utilise un `Providers` qui n'a aucune notion de thème dark (`SidebarProvider` only).
- `apps/azalee` utilise un `ThemeProvider` custom qui gère `roy`/`gaelle` via `<html class="roy">` + CSS vars `--theme-primary`, `--theme-secondary`, etc. Ces vars **ne sont pas mappées** sur les tokens shadcn (`--primary`, `--background`, etc.) → les composants ignorent le thème.
- 11 composants ont des classes `dark:` (chart, alert, switch, menubar, toggle, field, input-otp, kbd, input-group, context-menu, calendar) — elles s'activent uniquement si une classe `.dark` est sur un ancêtre. Aucune app ne fait ça aujourd'hui → toutes les variantes `dark:` sont mortes.

**Recommandations** :
1. Installer `next-themes` dans les 2 apps (ou un seul si azalee garde son système).
2. Réparer `sonner.tsx` pour respecter le `theme` du context (`useTheme()` de next-themes).
3. Brancher azalee `roy`/`gaelle` sur des sélecteurs `.roy`/`.gaelle` dans `globals.css` qui re-mappent **les tokens shadcn** (`--primary`, `--secondary`, `--accent`, …) — pas seulement des `--theme-*` parallèles que personne ne lit.
4. Ajouter un `<ThemeProvider>` standardisé dans `@rg/ui` qui wrappe `next-themes/ThemeProvider` + expose `<ThemeToggle />` (Sun/Moon dropdown).

### `radix-ui` umbrella vs sub-packages

11 composants importent depuis l'umbrella `radix-ui` (`{ Popover as PopoverPrimitive } from "radix-ui"`), 16 importent depuis les sub-packages `@radix-ui/react-*`. Les deux fonctionnent (l'umbrella ré-exporte tout), mais ce mix est inconsistant :
- **Sub-packages** = tree-shaking explicite, types plus précis, contrôle de version individuel.
- **Umbrella** = simplicité, version unique.

**Recommandation** : choisir un seul pattern. Le pattern shadcn upstream actuel utilise les sub-packages — privilégier ça. Ajouter les sub-packages manquants à `package.json` (`@radix-ui/react-popover`, `react-hover-card`, `react-context-menu`, `react-menubar`, `react-navigation-menu`, `react-toggle`, `react-toggle-group`, `react-progress`, `react-aspect-ratio`, `react-scroll-area`) et retirer `radix-ui` de l'umbrella si non utilisé ailleurs.
