## Méthode

- Avant : la prod (`https://rosegriffon.fr`, état d'avant ces commits), mesurée le 5/11 vers 12 h 30.

  (`BETTER_AUTH_URL=https://rosegriffon.fr NEXT_PUBLIC_SITE_URL=https://rosegriffon.fr NODE_ENV=production bun run build`, sortie 0),

## 1. JS de la coque (commit b1741e09)

Cause principale trouvée : `src/lib/utils.ts` faisait `export * from "@rosegriffon/ui"`. L'optimiseur de barils de Next ne
voit pas les noms à travers ce `export *` : chaque fichier client qui importait `cn` (105 fichiers) tirait les ~90 composants
du paquet, recharts compris (chunk `4421-*`, 272 Ko). Remplacé par `export { cn } from "@rosegriffon/ui/lib/utils"`.

Autres coupes :
- `RealtimeSettingsListener` (accueil) : `@/lib/realtime` (supabase-js, 171 Ko) importé au repos du navigateur (`requestIdleCallback`).
- `AchilleaAuthProvider` et la visibilité de la nav : client API Achilléa (et zod) importé à la demande ; la coque importe
  `@/lib/achillea/auth-context`, plus le baril.
- `LanguageProvider` : embarque `src/lib/i18n/fr-interface.json` (170 clés d'interface, 7 Ko) au lieu de `public/locales/fr.json`
  (4 204 clés, 256 Ko). Les 4 034 clés `0x…` (texte du jeu, 230 Ko) ne sont lues par aucun composant (aucun appel `t()`
  dynamique, aucune clé `0x…` dans `src/`). Le fichier est généré par `bun scripts/locales-interface.ts` ; le test
  `src/lib/i18n/fr-interface.test.ts` échoue s'il n'est plus synchrone avec fr.json, ou si une source se met à lire une clé `0x…`.
  en/ja restent chargés en entier à la demande, comme avant. Contrôle : aucune clé brute (`nav.*`, `wiki.*`…) dans le HTML de `/` et `/wiki/chara`.

## 2. `/news` : LCP de 14,5 s (52 s dans l'audit) (commit c05fc9b0)

Élément LCP (Lighthouse prod) : `section.space-y-3 > a.group > div.relative > img.object-cover`, l'image de la une (`FeaturedHero`).
Sa source, `https://cdn.rosegriffon.fr/dx11/menu/220_img/gallery_img2/img_story_ev02_main_0020.png?w=1600&format=webp`,
répond **502**. Le navigateur la chargeait, échouait, puis `onError` posait `/images/placeholder-news.svg` **après
l'hydratation** de tout le JS : l'élément LCP naissait côté client (« Request is discoverable in initial document : false »).

Correctif : `src/lib/images/disponibilite.ts` sonde au rendu les couvertures de la une et des articles (requête `Range: bytes=0-0`,
1,5 s max, en parallèle des lectures secondaires ; verdict mémorisé 30 min si servie, 2 min sinon ; un délai dépassé laisse sa chance à
l'image). Une couverture morte est remplacée par le visuel de repli dès le HTML. Les SVG ne passent plus par `/_next/image`.

| | Prod avant | Local après |
|---|---|---|
| `src` de l'image `fetchPriority="high"` dans le HTML | URL CDN en 502 | `/images/placeholder-news.svg` (200, 1 419 o) |
| Découvrable dans le HTML initial (Lighthouse) | non | oui |
| LCP simulé / observé | 14 568 ms / 2 235 ms | 5 933 ms (localhost) / 1 363 ms |
| TBT | 522 ms | 192 ms |
| Perf | 54 | 75 |

Le délai restant (`resourceLoadDelay` 889 ms) est le rendu serveur de la liste (requêtes Postgres distantes) derrière `loading.tsx`.

## 3. `/feed` : HTML retenu par la CLI X (commit 7432182c)

Causes :
1. La page attendait `lireFil()` avant tout octet ; un cache expiré (45 s) refaisait attendre la CLI `aphrody x`.
2. Un profil X en échec n'était pas mémorisé : chaque lecture relançait la CLI, et la source X attend profil **et** posts,
   donc toute la réponse restait bloquée le temps du délai de la CLI, même posts en cache. Mesuré avec la fausse CLI :
   `/api/feed/live?reseau=x&compte=InazumaCrossFR` à **20,0 s** alors que les posts étaient en cache.

Correctifs : `memo` en stale-while-revalidate (une valeur périmée de moins de 15 min sort tout de suite, relue en tâche de fond ;
même rythme d'appels réels), échec de profil retenu 2 min, page en streaming (Suspense) avec 2 s d'attente maximale des sources,
au-delà le client prend le relais et rejoint la lecture déjà en vol.

| `/feed?reseau=x&compte=…` (CLI X à 20 s) | Avant | Après |
|---|---|---|
| Prod, crawl du 5/11 | 12-52 s pour le HTML | - |
| Prod, ce matin (cache chaud) | TTFB 1 056 ms (`InazumaCrossFR`), 1 542 ms (`LEVEL5_times`) | - |
| Local, à froid | - | TTFB 15 ms, fin du HTML 2,0 s (squelette, puis le client) |
| Local, API après arrivée des posts | 20,0 s (avant le correctif du profil) | 11 ms |
| Local, page à chaud | - | TTFB 15 ms, total 16 ms, posts dans le HTML |

`/feed`, Lighthouse mobile : TTFB 4 175 → 45 ms, FCP observé 4 313 → 200 ms, LCP observé 5 681 → 2 048 ms (prod avant → local après).
